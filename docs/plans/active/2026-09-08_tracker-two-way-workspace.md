# Планировщик как рабочее место: двусторонняя работа с Яндекс.Трекером

## Metadata

- **Date**: 2026-09-08
- **Status**: In Progress
- **Complexity**: High
- **Progress**: 70%

## Context

Сейчас планировщик — зеркало Трекера только для чтения. Задачи приезжают cron-синком,
но все действия (приоритизация, заведение, закрытие, списание часов) делаются в веб-интерфейсе
Трекера. Хочется, чтобы утро и вечер проходили в боте: утром отранжировал день перетаскиванием,
вечером одним экраном списал часы и закрыл сделанное.

Отдельно нужно развести два потока задач: внутренние (из Obsidian-vault `tasks.md`) и рабочие
(из Трекера), с возможностью «поднять» внутреннюю задачу в Трекер.

### Что уже работает

- Pull-синк активных задач по cron (`/api/cron/tracker-sync`).
- Закрытие DONE → transition в Трекере (`closeIssue` в `src/lib/tracker/client.ts`).
- `tasks.externalSource` уже различает источник: `NULL` = внутренняя, `yandex-tracker` = рабочая.
- Проекты подтягиваются из Obsidian (`scripts/sync-vault-projects.ts`), есть `slug`/`vaultPath`.
- Drag-n-drop (`@dnd-kit`, `SortableTaskList`) — но только в «Моём дне» (`myDaySortOrder`).

### Диагностика на живой орге (08.09.2026, org 7026646 vodohod.ru)

Замеры через API Трекера показали два дефекта, из-за которых разделы наполнились бы мусором:

1. **Фильтр активных сломан.** Прод использует `Assignee: me() AND Resolution: empty()`.
   Этот запрос вернул 10 тикетов, из которых 8 закрытых (POLAERP-2/17/28/42/55, SHWEB-144/266,
   AIBOT-121 «Отменено»). Правильный результат даёт
   `Status: !closed AND Status: !cancelled AND Status: !resolved` — ровно 17 активных из 62 всего.
2. **Поисковый индекс отдаёт неконсистентные статусы.** Один и тот же POLAERP-42 в одном ответе
   «В работе», в другом «Закрыт»; POLAERP-8/9 появились в выборке с фильтром, но отсутствуют
   в полном списке 62 тикетов. Вывод: одного YQL недостаточно, нужна клиентская проверка
   по `status.key`.
3. **Хардкод маппинга теряет 11 из 17 активных задач.** В `QUEUE_TO_PROJECT_SLUG` только
   `POLAERP`, а активные задачи лежат в четырёх очередях: POLAERP (6), REVENUERADAR (9),
   WEBSH (1), VDHWEBNEW (1).

### Questions and Answers

**Q:** Как должен выглядеть порядок задач на главном экране?
**A:** Один сквозной список всех задач с ранжированием перетаскиванием; проект — бейдж на карточке.
Дополнительно: разделить на два раздела — внутренние задачи (Obsidian) и задачи Трекера.

**Q:** Как удобнее вводить списание часов?
**A:** Из скилла `/timesheet` с подтверждением: он уже считает «задача → часы» по сессиям Claude Code
и дефицит до нормы рабочего дня. Планировщик показывает готовую разбивку, пользователь правит и жмёт «Списать».

**Q:** Куда попадает новая задача, заведённая в планировщике?
**A:** Локально, с кнопкой «поднять в Трекер» — мелочь, которую не хочется тащить в Трекер,
остаётся внутренней.

**Q:** Что делать с vault `tasks.md`?
**A:** Vault для своего (интур, vodohod-new-site, tg-planer), Трекер для рабочего. Два потока,
граница фиксируется явно.

**Q:** Где хранить связь Obsidian-проект ↔ очередь Трекера?
**A:** Конфигом, который подтягивается из Obsidian: проекты и так берутся из vault, туда же
ложится список очередей пользователя.

## Solution

Связь проект↔очередь переносится из кода в **frontmatter `index.md`** проекта в vault:

```yaml
tracker_queues: [POLAERP]        # откуда тянуть задачи в этот проект
tracker_default_queue: POLAERP   # куда «поднимать» внутренние задачи
```

Плоские ключи (не вложенный `tracker:`) — потому что самописный парсер frontmatter
в `sync-vault-projects.ts` поддерживает inline-массивы, но не вложенные объекты. `pnpm sync:vault`
заливает это в новые поля `projects.trackerQueues` / `projects.trackerDefaultQueue`, а синк строит
маппинг «очередь → проект» запросом к БД. Добавить очередь = дописать строку в `index.md`,
без правки кода и деплоя.

Фильтр активных становится двухслойным: YQL-запрос с исключением статусов **плюс** клиентская
проверка `status.key` — из-за неконсистентности поискового индекса. Задачи, пропавшие из выборки
активных, закрываются локально (reconciliation) — это же чистит уже натёкший мусор.

### Alternatives

1. **Маппинг в таблице БД + только UI настроек** — отвергнуто: конфиг не версионируется в git
   и расходится с vault, который пользователь считает источником истины по проектам.
2. **Вложенный frontmatter `tracker: { queues: [...] }`** — отвергнуто: пришлось бы переписывать
   парсер frontmatter под вложенность, риск сломать разбор `repos:` у мультирепо-проектов.
3. **Только YQL-фильтр без клиентской проверки** — отвергнуто: замеры показали, что индекс
   Трекера отдаёт разные статусы для одного тикета.
4. **Приземлять задачи Трекера в `tasks.md`** (vault главный для всего) — отвергнуто:
   двусторонний синк через файлы даёт конфликты на каждом изменении статуса.
5. **Двусторонний синк порядка задач с досками Трекера** — отвергнуто: порядок в досках свой,
   ранжирование остаётся локальным свойством планировщика.

## Consequences

### Positive
- Приоритизация, заведение, закрытие и списание часов — в боте, без веб-интерфейса Трекера
- Новая очередь подключается строкой в настройках бота, без правки кода и деплоя
- В планировщик перестанут течь закрытые тикеты, а закрытые в Трекере будут закрываться локально
- Перестанут теряться 11 из 17 активных задач (REVENUERADAR, WEBSH, VDHWEBNEW)
- Внутренние и рабочие задачи разведены явно, с мостом «поднять в Трекер»

### Risks
- **Reconciliation может закрыть лишнее**, если синк однажды станет частичным (`updatedSince`) —
  тогда «пропавшая» задача не значит «закрытая». Пометить зависимость в коде явным комментарием
  и не включать `updatedSince` без пересмотра этой логики.
- **Неконсистентный индекс Трекера** может на одном прогоне отдать устаревший статус. Отсюда
  двухслойная проверка; статус DONE локально не откатываем обратно в TODO.
- **Запись в Трекер — внешнее действие.** Worklog и создание тикетов — только по явной кнопке,
  никогда автоматически из cron.
- **Миграции на прод только через GitHub Actions** (`.github/workflows/db-migrate.yml`), вручную не накатывать.

### Technical Debt
- Правка конфига очередей из UI (write-back в `index.md`) отложена: на первом этапе конфиг
  правится в Obsidian, UI только читает.
- Уведомления об изменениях задач (Этап 2 tracker-notify) остаются отложенными.
- Порядок задач не синхронизируется с досками Трекера — сознательно.
